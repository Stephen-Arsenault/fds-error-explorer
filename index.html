Where the problem lives

How an FDS disk loads

The Famicom Disk System was a 1986 add-on that let Nintendo's console load games from a small floppy disk instead of a cartridge. When you switch it on, a program burned into the console-side hardware — the BIOS — spins up the drive, reads the game off the disk into memory, and starts it.

The data on a disk is written as a series of blocks, read strictly in order: an identification block naming the game, a count of how many files follow, then for each file a small header followed by the file's data.

The BIOS checks something at nearly every step. If a check fails it stops the drive and puts a two-digit number on screen — sometimes with a word above it, often without. That number is what this page decodes.

Behaviour is traced from one 8 KB BIOS image by static analysis; nothing was executed or emulated, and addresses are the ROM's own, mapped at $E000. Where a field's meaning is inferred from its position rather than confirmed by the ROM's own text, the entry says so.

Some details cannot be derived from the ROM at all — what the disk's header fields are called, what the media physically looks like, and how the drive senses it. Those come from the NESdev Wiki and community hardware documentation.

Exactly what came from those sources
  • The disk-info header's field names and offsets ($0F licensee code through $18). Which error code guards which byte is from the ROM; the names are the format spec's. Only $07 (side) and $08 (disk number) are independently confirmed by the BIOS's own message strings.
  • The two values of the disk type field at $17 — $01 for blue-disk (FMC) releases, $00 otherwise.
  • That the field at $18 has no known purpose and reads $00 on every commercial game examined. That is essentially all of ERR.10.
  • The write-protect tab: where it sits on the card, that a broken tab means protected, the tape repair, and the sensing lever that misreports when dirty.
  • That the protect bit in $4032 also reads 1 for an ejected disk.
  • Blue Disk Cards: the sliding shutter, the missing top-edge protrusion, and the Disk Fax high-score service they were made for.

ERR.01 — The drive doesn't think there's a disk in it

Where the problem lives: Drive & power · When: at start-up and during play · On screen: DISK SET / ERR.01

What it means

The drive says there is nothing in it. It never looks at the disk — it feels for a small switch that a disk presses when pushed all the way in.

So a disk that is not fully seated, or a worn switch, looks the same as an empty slot. That is why you can be looking straight at a disk and still get this.

What triggers it

Checked when the drive starts up, and again after every chunk of data it reads. Taking the disk out mid-load gives the same result as never inserting one.

Worth knowing

  • Push the disk firmly all the way in. That is usually all it takes.
  • The system cannot tell 'no disk' apart from 'disk in, switch not pressed'.
Technical detail

The drive reports its state in a status register at $4032; bit 0 is the disk-present line. The BIOS only reads that bit — nothing in the ROM touches the sensing mechanism itself.

Raise site
$E678 DriveReadyWait · $E42A SetupWriteParams · $E757 WriteBlockEnd
Condition
$4032 bit 0 set
Detail
Carry gate at $E77C from DriveReadyWait and WriteBlockEnd; return-address discard at $E43E from the API prologue.

ERR.02 — The drive isn't receiving proper power

Where the problem lives: Drive & power · When: at start-up and during play · On screen: BATTERY / ERR.02

What it means

The drive is not getting the power it needs. This is tested before the disk is touched at all.

BATTERY on screen is too specific. The unit runs from batteries or a mains adapter and this appears either way, so read it as 'power'.

What triggers it

The system sends a signal to the drive and listens for it coming back. Anything breaking that path counts: a dead adapter, flat batteries, corroded contacts, dirty connectors.

Worth knowing

  • Nothing to do with the disk — this happens before the disk is read.
  • Also appears when power is present but not reaching the drive properly.
Technical detail

Not a voltage measurement. The BIOS drives bit 7 out to the expansion connector at $4026 and reads the same line back from $4033, so what is really being tested is a loopback across that path.

Raise site
$E669 DriveReadyWait
Condition
write $F9|$80 → $4026, then EOR $4033, test bit 7
Detail
Carry gate at $E77C.

ERR.03 — Something tried to save to a protected disk

Where the problem lives: Drive & power · When: only from a running game · On screen: ERR.03 with no message line

What it means

A game tried to save, and the disk is set to refuse writes. Nothing was written and nothing was harmed.

To check: hold the disk as it goes into the drive and look at the top-left corner of the side facing in. A small tab there means writing is allowed. A gap where it used to be means protected.

What triggers it

Only checked when saving. Loading ignores it, so a protected disk plays normally and fails the moment a game tries to save.

Worth knowing

  • Hole open = protected. Cover it with tape to allow writing again; the tab does not go back on.
  • The drive feels for the tab with a small lever, which can stick when dirty and report protection on a perfectly good disk.
Technical detail

The protect state arrives as bit 2 of the drive status register $4032. That same bit reads 1 for an ejected disk, so at this bit alone the two conditions cannot be told apart.

Raise site
$E435 SetupWriteParams
Condition
$4032 bit 2 set (Protect flag)
Detail
Reached only when the read/write flag is clear; $E433 BCS skips it for reads. Per the NESdev Wiki the same flag reads 1 for a broken tab or an ejected disk.

ERR.04 — The disk was published by someone other than the game expected

Where the problem lives: Wrong disk · When: only from a running game · On screen: ERR.04 with no message line

What it means

The disk was made by a different publisher than the game asked for.

In practice: a game asked you to swap disks and got something unrelated.

What triggers it

A game can name the disk it expects before loading from it. The system compares what is written on the disk against that and stops at the first thing that does not match.

Worth knowing

  • Games choose which details to check, so many never produce this at all.
Technical detail

A caller passes a ten-byte template describing the disk it expects, and CheckDiskHeader walks the disk's identity fields against it. A template byte of $FF is a wildcard and skips that comparison. The error code is a counter that advances through the walk, which is how each field gets its own number.

Raise site
$E445 CheckDiskHeader, byte 0 (header offset $0F)
Condition
disk byte ≠ caller template byte, and template byte ≠ $FF
Detail
Code comes from the running counter in $08, initialised to 4. Boot template at $EFF5 is FF FF FF FF FF FF 00 00 FF FF.

ERR.07 — The disk is in the wrong way round — flip it

Where the problem lives: Wrong disk · When: at start-up and during play · On screen: A·B SIDE / ERR.07

What it means

The disk is in the wrong way round. Each side holds different data, so a side works like its own disk.

Take it out, turn it over, put it back. Starting the system with the B side facing in gives this too.

What triggers it

Disks record which side is which. The system, or the game you are playing, wanted the other one.

Worth knowing

  • If a game asks you to flip and you put the same side back in, you will see this again.
  • One of only four errors that names the problem on screen instead of showing a bare number.
Technical detail

A caller passes a ten-byte template describing the disk it expects, and CheckDiskHeader walks the disk's identity fields against it. A template byte of $FF is a wildcard and skips that comparison. The error code is a counter that advances through the walk, which is how each field gets its own number.

Raise site
$E445 CheckDiskHeader, byte 6 (header offset $15)
Condition
disk byte ≠ caller template byte, and template byte ≠ $FF
Detail
Message string 'A.B SIDE' at $F02E+16. Boot template byte 6 at $EFF5 is $00, not a wildcard.

ERR.09 — This is the wrong kind of disk

Where the problem lives: Wrong disk · When: only from a running game · On screen: ERR.09 with no message line

What it means

There were two kinds: ordinary yellow disks, and blue ones. A game wanted one kind and got the other.

Blue disks have a sliding cover over the opening and no small tab along the top edge, so they are easy to tell apart by eye.

What triggers it

Blue disks were made for Nintendo's national high-score contests — you carried them to a kiosk that read your score off the disk. Only those games check this, which is why it is so rarely seen.

Worth knowing

  • Both kinds are perfectly good disks. This is not damage.
Technical detail

A caller passes a ten-byte template describing the disk it expects, and CheckDiskHeader walks the disk's identity fields against it. A template byte of $FF is a wildcard and skips that comparison. The error code is a counter that advances through the walk, which is how each field gets its own number.

Raise site
$E445 CheckDiskHeader, byte 8 (header offset $17)
Condition
disk byte ≠ caller template byte, and template byte ≠ $FF
Detail
Documented as 'disk type (FMC)': $01 for FMC blue-disk releases, $00 otherwise.

ERR.10 — An unidentified detail on the disk does not match

Where the problem lives: Wrong disk · When: only from a running game · On screen: ERR.10 with no message line

What it means

One of the details written on the disk is not what the game expected — and it is the one detail nobody has worked out the purpose of.

It reads as zero on every commercial game anyone has examined.

What triggers it

It would take a game deliberately demanding something unusual here, which no known release does. In practice it points to a homemade or altered disk.

Worth knowing

  • Very rarely seen.
Technical detail

A caller passes a ten-byte template describing the disk it expects, and CheckDiskHeader walks the disk's identity fields against it. A template byte of $FF is a wildcard and skips that comparison. The error code is a counter that advances through the walk, which is how each field gets its own number.

Raise site
$E445 CheckDiskHeader, byte 9 (header offset $18)
Condition
disk byte ≠ caller template byte, and template byte ≠ $FF
Detail
Documented as unknown, $00 in all known games. $E45B rewrites the counter value $0A to $10 before the gate.

ERR.20 — The game loaded fine but didn't show the required Nintendo screen

Where the problem lives: Software rule · When: start-up only · On screen: DISK TROUBLE / ERR.20

What it means

Nothing is wrong with the disk. It loaded perfectly and the game is already in memory.

Before starting a game, the system checks that the game has drawn Nintendo's copyright notice on screen. If it has not, the system refuses to run it.

What triggers it

It compares what the game has put on screen against a copy held inside the console. One character out of place is enough. Unlicensed disks that skipped the notice stop here.

Worth knowing

  • The screen still reads DISK TROUBLE, which is misleading — the disk is fine.
Technical detail

The check compares $E0 bytes of the game's own nametable at VRAM $2800 against a tile table at $ED37. It runs from RESET after LoadFiles has already returned success, which is why it is a boot-path gate and unreachable from a running game.

Raise site
$EF6A RESET (raised) → $F431 CopyrightCheck (decided)
Condition
video memory $2800–$28DF ≠ tile table at $ED37
Detail
$ED37 spells 'NINTENDO' and 'FAMILY CO…' in the BIOS tile encoding.

ERR.21 — This does not look like a Famicom disk

Where the problem lives: Unreadable data · When: at start-up and during play · On screen: DISK TROUBLE / ERR.21

What it means

Every genuine Famicom disk begins with the same fourteen-character marking. This one does not carry it.

Either it is not a Famicom disk, or the very beginning of it is too damaged to read.

What triggers it

The system reads those first fourteen characters and compares them one at a time against a copy held inside the console.

Worth knowing

  • What you would expect from a blank disk, a badly worn one, or a disk from another system.
Technical detail

The 14-byte magic string is held reversed at $E6D5, because the compare loop counts Y down from $0D while the disk streams forward. One constant code covers all fourteen comparisons.

Raise site
$E6FA ReadVerifyDiskInfo
Condition
disk byte ≠ table byte at $E6D5+Y, for Y = $0D down to 0
Detail
The table stores '*NINTENDO-HVC*' reversed, because the loop counts down while the disk streams forward.

ERR.22 — The part of the disk that names the game is missing

Where the problem lives: Unreadable data · When: at start-up and during play · On screen: DISK TROUBLE / ERR.22

What it means

A disk stores its data as a run of labelled sections, read in a fixed order. The first should be the one naming the game, and it is not.

Since this is the very first thing read, it usually means the disk is unreadable from the start rather than damaged partway through.

What triggers it

The system checks each section's label before reading it, and this one was not what should come first.

Worth knowing

  • ERR.22 to ERR.25 are the same check at four points in the sequence.
Technical detail

Every block opens with a type byte: 1 disk info, 2 file amount, 3 file header, 4 file data. ReadBlockType computes the error as blocktype + $21, which is why these four form a contiguous run.

Raise site
$E697 ReadBlockType
Condition
tag byte read ≠ expected block type
Detail
Code = block type + $21 via CLC / ADC #$21.

ERR.26 — A save did not record properly

Where the problem lives: Saving failed · When: only from a running game · On screen: DISK TROUBLE / ERR.26

What it means

The system reads back everything it writes and compares the two. They did not match, so the save cannot be trusted.

Usually a worn disk surface, or a drive that has drifted out of alignment.

What triggers it

Every save is checked by reading it straight back. A single byte out of place stops the operation.

Worth knowing

  • It cannot tell you which part of the save failed.
Technical detail

WriteVerifyBlock re-reads each written byte and compares it against whichever source it came from — the file header, the caller's parameter list, CPU RAM via [$0A], or PPUDATA. Four separate compare sites share the one code.

Raise site
$E5C0 · $E5D2 · $E5FC · $E62B, all in WriteVerifyBlock
Condition
byte read back ≠ byte written
Detail
All four go through the zero gate at $E77F.

ERR.27 — Part of the disk read back damaged

Where the problem lives: Unreadable data · When: at start-up and during play · On screen: DISK TROUBLE / ERR.27

What it means

The system checks its own arithmetic on every chunk of data it loads, and on this one the numbers did not agree. At least one byte came back wrong.

This is the usual sign of a worn, scratched or dirty disk, and the most common reason an old disk stops loading.

What triggers it

Checked after every chunk. The system tries twice before reporting it, so the damage is consistent rather than a passing glitch.

Worth knowing

  • Cleaning the disk is worth trying. Beyond that, the data itself has degraded.
Technical detail

Each block ends with a CRC. The BIOS arms CRC-check mode via FDS_CONTROL bit 4, reads one further byte, then tests $4030 bit 4. A read is attempted twice ($0005 = 2) before the code escapes to the caller.

Raise site
$E71E CheckBlockEnd
Condition
$4030 bit 4 set after arming CRC control
Detail
Reached by a raw branch to $E781, bypassing both throw gates.

ERR.28 — Data stopped sooner than expected

Where the problem lives: Unreadable data · When: at start-up and during play · On screen: DISK TROUBLE / ERR.28

What it means

A chunk of data ended while the system was still expecting more of it — there is less on the disk than the disk itself claimed.

Usually damage, or the drive losing its place partway through.

What triggers it

The system watches for an end marker while reading, and saw it before it had read everything it was told to expect.

Worth knowing

  • Different from ERR.27: this is data that is too short, that is data that is wrong.
Technical detail

$4030 bit 6 is the end-of-block mark. Two sites in the read path test it — the block trailer check and the byte-copy loop — and both branch straight into the abort at $E781, bypassing the usual gates.

Raise site
$E709 CheckBlockEnd · $E766 ReadBlockToRAM
Condition
$4030 bit 6 set while bytes remain
Detail
Both sites branch raw to $E781.

ERR.29 — The disk ran out of room while saving

Where the problem lives: Saving failed · When: only from a running game · On screen: DISK TROUBLE / ERR.29

What it means

A save stopped partway because there was no more space to write into.

What triggers it

The drive signalled the end of the writable area before the system had finished writing.

Worth knowing

  • The save is incomplete and the disk is left partly written.
  • ERR.28 is this same thing happening while loading.
Technical detail

The same $4030 bit 6 end-of-block mark that produces ERR.28, tested on the write side instead.

Raise site
$E72C WriteBlockEnd
Condition
$4030 bit 6 set during a write
Detail
Raw branch to $E781.

ERR.30 — The drive stopped being ready during a save

Where the problem lives: Saving failed · When: only from a running game · On screen: ERR.30 with no message line

What it means

The drive stopped being ready partway through a save, so the save did not finish.

What triggers it

After writing, the system pauses briefly and then asks the drive whether it is still ready. It was not.

Worth knowing

  • The pause is a fixed length rather than a measured one, so a marginal drive may pass or fail it inconsistently.
  • The screen shows only the number, with no message above it.
Technical detail

Tests $4032 bit 1 (drive not ready) after a busy wait of roughly 178 loop iterations. That delay is instruction-counted rather than timed, so its real duration varies with the machine.

Raise site
$E743 WriteBlockEnd
Condition
$4032 bit 1 set after a busy wait of ~178 iterations
Detail
Raw branch to $E781.

ERR.31 — A program asked for more files than the disk holds

Where the problem lives: Software rule · When: only from a running game · On screen: ERR.31 with no message line

What it means

A game asked for more files than the disk holds. Nothing is broken — the request was impossible.

What triggers it

The system counts what is on the disk and compares it against what was asked for.

Worth knowing

  • Nothing is interrupted: the drive keeps running and the game simply gets a refusal back.
  • The screen shows only the number, with no message above it.
Technical detail

AdjustFileCount subtracts the requested count from the count present and returns the code in A via TXA/RTS at $E2F5. It never enters the throw block at $E778, so the drive is left running.

Raise site
$E2DE AdjustFileCount
Condition
requested count > count present on disk
Detail
Returned via TXA / RTS at $E2F5, never through the throw block at $E778.
